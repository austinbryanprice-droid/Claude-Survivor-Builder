# Architecture rules

Multiplayer arrives in Phase 3, before any gameplay exists, so the code is network-ready from Phase 2. These rules keep that from becoming a rewrite. Change one only with a note in [decisions.md](decisions.md).

## Layers

Each layer may import only the layers listed. ESLint enforces the boundaries (`eslint.config.js`).

| Folder        | Holds                                                                                                                        | May import                   |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------- | ---------------------------- |
| `src/shared`  | Pure TypeScript: hashing, seeded random numbers, math, URL flags, protocol types                                             | nothing else in `src`        |
| `src/engine`  | Renderer, camera, input, game loop, anything that touches three.js or the DOM                                                | `shared`, three              |
| `src/world`   | Voxel data, seeded terrain, chunks, meshing, materials                                                                       | `shared`                     |
| `src/systems` | Survival, waves, economy, upgrades: the host simulation                                                                      | `shared`, `world`            |
| `src/net`     | Transports (loopback and PeerJS), commands, events, snapshots                                                                | `shared`, `world`, `systems` |
| `src/ui`      | HUD, menus, overlays in HTML and CSS                                                                                         | every layer                  |
| `src/app`     | The composition root: reads the URL and the saved settings, builds the stage, the world and the HUD, and wires them together | every layer                  |

`world`, `systems` and `net` never import three.js or touch the DOM, so they run in a Worker and under Vitest. The thin render adapters in `src/world/render` are the exception: they may import `engine` and three.js. `engine` never imports `world`, `systems`, `net` or `ui`; `src/app` is where they meet.

## The rules

1. **One command path.** Every change to the world is a command (place, break, upgrade, harvest, attack). The host validates it and turns it into events, and every peer, the host included, applies the same events. Single-player is the host session with nobody in the room, tests run whole rooms over an in-memory transport, and PeerJS is the real one (`src/net`, [multiplayer.md](multiplayer.md)).
2. **Terrain is a function of a seed.** Integer-hash noise (`src/shared/hash.ts`), never `Math.sin` tricks or `Math.random`, so every browser generates identical terrain. A late-join snapshot and a save are the seed plus edited chunks, entities and the economy: kilobytes, not megabytes. Retry reuses the seed; New Run draws a new one.
3. **Two meshing paths.** Terrain is a smooth surface-nets mesh with baked vertex AO. Player structures get per-face inset and chamfer geometry with no greedy merging, so panel seams stay. `InstancedMesh` serves modules, enemies, projectiles and particles. Only dirty chunks and their neighbors are remeshed.
4. **Content is data.** Blocks, tiers, modules, costs, enemies, waves and timers live in plain TypeScript tables. A headless balance simulator in Vitest (`src/systems/economy/simulator.ts`, run by `npm run balance`) prints income against cost per night, so tuning is checked rather than guessed.
5. **Fixed-step host.** The host simulates at 20 Hz in fixed steps, fed real time with a catch-up limit, so a slow tab plays the same run as a fast one; the plan is a Worker so a hidden tab does not freeze everyone (what Phase 4 decided about it is in [decisions](decisions.md#phase-4a-the-day-and-night-clock-2026-10-21), and what a full field of machines costs the host is measured in [4d](decisions.md#phase-4d-the-crawler-2026-10-23)). Rendering runs at display rate with interpolation. The host sees a warning when its tab is hidden.
6. **Two channels.** An ordered channel carries edits and events, and the shots of the pulse blaster (a `fire` command in, an `sh` report out: the host judges the bolt against the machines as the shooter's screen drew them, so a shot that looked true is one). An unordered one (PeerJS `reliable: false`) carries player transforms (about 20 Hz) and enemy transforms (about 10 Hz) as quantized binary, and stale packets are dropped by sequence number. PeerJS cannot give truly lossy delivery. Clients own their movement and the host sanity-checks it; the host owns blocks, costs, enemies, waves, health and research. Broker and ICE servers are configurable by URL parameter (`?broker=`, `?ice=`), and room codes are prefixed and retried on collision. Every number lives in one table (`NET` in `src/shared/net-config.ts`).
7. **Tunable and testable.** One balance file, URL switches for development (`?night=5`, `?bench=1`, `?debug`), and no gameplay that needs the console.
8. **Movement and collision are shared code.** The player controller, the swept box collision and the fixed-step clock live in `src/shared` and read the world through two queries: `SolidQuery` (`isSolid(x, y, z)` on integer cells, for blocks) and `GroundQuery` (distance, push-out and snap-down against the smooth terrain). Together they are a `CollisionWorld`. The engine uses them for the local player, and the host can run the very same code to sanity-check a client's movement. The engine runs them at 60 Hz and draws the frames in between by interpolation; the host's 20 Hz world tick (rule 5) is separate.
9. **The engine knows no world.** `Stage` (renderer, sky, sun, presets) and `Game` (the fixed-step loop, the local player, the camera) take the world as a `GameWorld`: its collision, spawn point, benchmark route and build timings. `src/app` builds the real one (`createValleyWorld`: the terrain, the voxel world on top of it, and the view that draws the terrain and the blocks), so a test deck, an empty plane and the valley all fit, and `Game.loadWorld(seed)` swaps one for another. The net layer drives the game through `teleport`, `loadWorld`, `onTick` and `onBeforeRender`.
10. **The net layer reaches the game through `src/app`.** `src/net` knows sessions, transports and the `BlockWorld` interface, nothing of three.js, the DOM or `Game`. `src/app/multiplayer.ts` joins the lobby, the player's movement, the other players' avatars and the room panel, and asks the game for four narrow views (the player, the world, the scene and the mouse); `src/app/attach-multiplayer.ts` is the only file that builds those views from a `Game`. It loads on demand after the game has started, and never with `?bench=1`, so the benchmark measures the game alone. New commands (upgrade, place a module) are new command shapes validated by the host session; the build controls call `session.sendCommand` and listen for events, and never touch a socket.
